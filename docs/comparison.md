# 对比

> English summary: this page compares mechanisms, not code, with mem0 (LLM-decided
> ADD/UPDATE/DELETE over vector neighbours), MemOS (memory as a scheduled resource,
> including parametric forms), Zep / Graphiti (bi-temporal knowledge graph, invalidation
> instead of deletion) and TencentDB Agent Memory (a service-shaped, database-backed
> memory layer). What changqing borrows, what it deliberately leaves out, and why.

这一页只比**机制**，不比实现，也不引任何一方的代码。四份对照的对象是 mem0、
MemOS、Zep / Graphiti、TencentDB Agent Memory —— 它们各自解决的是同一族问题，
选择不同。**凡涉及别家设计的描述以它们自己的文档为准**：这一页写的是「读它们
的设计时我们记下了什么、我们的取舍是什么」，不是它们现在的实现细节。

先说结论：这个库的机制几乎都能在这四家身上找到出处 —— 它的特点不在发明，
而在**把几条结论落到一个零依赖、可嵌入的库里，并且把「不编」这件事做成可验证的**
（每条事实带 `turn_ref` + `quote`，见 [抽取](extraction.md)）。

## mem0 · 动作集相同，落法不同

| | mem0 | changqing |
|---|---|---|
| 单元 | 一句被抽出来的事实，可按 `user_id` / `agent_id` / `run_id` 分作用域 | 一条三段式事实（`subject` / `predicate` / `object`），按 uid 分 |
| 写入 | 新候选先跟已有记忆做近邻，然后**由模型挑一个动作**：ADD / UPDATE / DELETE / NONE | 同样是模型挑动作（我们有 ADD / SUPERSEDE / NOOP，见 [抽取](extraction.md) 的闸 6） |
| 动作怎么落 | 直接改存储里那条 | **写成一条只追加的操作**；旧的那条标失效、**不删** |
| 读取 | 向量检索（可选叠图） | 槽位 + 全文 + 向量三路，RRF 融合后按画像与时间重排 |

**我们对齐它的**：公开面上的 `add` / `search` / `get` / `get_all` / `update` /
`delete` / `history` 这一套名字（见 [API](api.md)）—— 写惯了它的人不必先学一套新词。

**我们不一样的地方值得展开**：「直接改」与「追加一条操作」在**当下**看不出区别，
差别在事后。「他以前说过什么」这个问题，直接改就没有答案了；追加操作则保留了
整条时间线，而且日志本身可以重放出任意时刻的视图。代价是盘上多一份日志、
写路径多一步物化。

## MemOS · 记忆是被调度的资源

MemOS 的着眼点比「记住事实」大一层：它把记忆当成**要被调度的资源**，
有显式的调度层管生成、激活、融合、归档，并且把记忆分成明文 / 激活 / 参数三种形态
（后者包括推理时的 KV-cache 一类）。这是一个记忆操作系统的形状。

我们只取其中一句：**生命周期必须有显式的调度，而且调度必须能被观测**。
落法是 `worker` 的三个触发条件、`consolidate` 的衰减与合并、以及 `stats()` 里
那些能看见的数（见 [架构](architecture.md)）。

**我们不做的**：参数形态那一支。KV-cache 属于推理侧的管辖范围，一个可嵌入的
记忆库碰不到它 —— 硬要在库里描述它，只会多出一堆无法验证的字段。

## Zep / Graphiti · 双时间，比我们多一半

Zep 与它的引擎 Graphiti 把记忆建成**双时间**的知识图谱：一条边既记「事情何时为真」
（`valid_at` / `invalid_at`），也记「我们何时知道它」（`created_at` / `expired_at`），
并且用**失效而不是删除**来表达世界变了。检索上叠了图遍历。

**我们对齐它的**：失效不删这条结论，以及双时间里的**一半** —— 我们的
`valid_from` / `valid_to` 回答「这条当时是不是真的」，靠操作日志的时间戳回答
「我们什么时候知道的」。

**我们不做的**：实体消解与图。没有实体节点、没有边、没有社区摘要（见下面
「刻意不做」）。换来的是另一条更窄、但更硬的承诺：**每条事实都能回引到产生它的
那一轮原话**。图上对应的是「边 → episode」那条引用，只是我们不建图。

检索路线也因此不同：图是**按关系走**，我们是**三路并行 + RRF 融合**
（槽位 / 全文 / 向量），再按画像权重与时间衰减重排（见 [检索](retrieval.md)）。
两种都能回答「跟这句话有关的事」，图擅长多跳，我们擅长「哪一轮说过」。

## TencentDB Agent Memory · 服务与库的分野

这一类项目的形态是**服务**：以数据库为基座，把记忆做成一个长在云上的层，
分层存储 + 混合检索，外面挂多个 Agent。它解决的问题里有一半是运维问题 ——
多租户、配额、统一升级、跨语言接入。

我们刻意走另一条路：**库**。`pip install` 就进进程，没有额外要部署的东西，
没有网络跳数，一个 uid 一个目录（见 [存储](storage.md)）。

这是取舍而不是高低：

| | 服务化 | 库（本项目） |
|---|---|---|
| 多租户 / 统一运维 | 天生的 | 由宿主负责（一个 uid 一个目录） |
| 接入成本 | 一个 SDK 加一个部署 | 一次安装 |
| 每轮延迟 | 至少一次网络往返 | 本地文件 + 一次 SQLite 查询 |
| 升级 | 服务侧统一升 | 宿主自己升依赖 |

**我们对齐它的**：分层 + 混合检索，以及「原话与提炼分开存」。

## 刻意不做

上面几条里没被抄下来的部分，都是有理由的，不是遗漏：

| 不做 | 为什么 |
|---|---|
| **知识图谱**（实体消解、边、社区摘要） | 它换来的多跳能力，与「她记得住上一句」这个目标关系不大；而实体消解做不好会**静默**把两条事实并成一条 |
| **参数记忆 / KV-cache** | 属推理侧，一个库碰不到；写进接口只会多出一堆无法验证的字段 |
| **服务化框架依赖** | 「装上就能用」是核心卖点；引一个服务框架进来就等于要求每个宿主先部署一次 |
| **前端** | 界面是宿主的形状。这个库只提供可挂载的相对路径路由（见 [API](api.md)） |
| **多租户配额、跨语言 SDK** | 库的边界之外；宿主拿 uid 就能自己分租户 |

## 一句话对照

| 系统 | 最该记住的那一句 |
|---|---|
| mem0 | 让模型挑动作（ADD / UPDATE / DELETE / NONE）—— 我们抄了动作集，把落法改成只追加 |
| MemOS | 记忆是需要调度的资源 —— 我们抄了「显式调度 + 可观测」，没抄参数形态 |
| Zep / Graphiti | 双时间 + 失效不删 —— 我们抄了后半句与半个双时间，没抄图 |
| TencentDB Agent Memory | 服务化的记忆层 —— 我们抄了分层与混合检索，形态上反过来做库 |
| **changqing** | 每条事实都能追回那句原话；只有两样不可再生 |
