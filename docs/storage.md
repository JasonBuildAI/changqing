# 存储

> English summary: L0 raw utterances live in an append-only daily log that is archived but
> never deleted, L1 is an append-only operation log plus a rebuildable SQLite projection,
> and L2 summaries and L3 weights are derived. Only the first two cannot be regenerated,
> so a backup only needs those two.

这一页讲**盘上到底躺着什么**，以及「删」这个字在每一层各是什么意思。
为什么需要它：归档、重建、忘记这几件事在代码里各自只有几行，判断它们对不对
却要看落盘格式 —— 格式变了而调用方不知道，是一种**不报错**的缺陷。

## 一棵树

```
{root}/                          # 默认 ~/.changqing；CHANGQING_DIR 覆盖
└── {uid[:2]}/                   # 按 uid 前两位分桶，避免一个目录塞十万个用户
    └── {uid}/
        ├── state.json           # 序号 + 整理游标（小可变文件，原子写）
        ├── sessions/
        │   ├── 2026-03-05.md    # L0 原话，一天一个文件，只追加
        │   └── 2026-03-06.md
        ├── sessions.archive/
        │   └── 2026-01-05.md.gz # 超期整月搬到这里，一个字节都不删
        ├── log.jsonl            # L1 操作日志（唯一事实源，只追加）
        ├── index.sqlite         # 物化视图（删了能重建）
        ├── facts.md             # 渲染视图（给人看的，可重建）
        ├── summaries.md         # L2 纪要的渲染视图
        └── topics.md            # 主动话题的渲染视图
```

`uid` 会先过一道白名单（`paths.safe_name`：只留字母数字与 `_` `-`）才拼进路径。
多这一道的成本是零，少这一道就是路径注入。

## 只有两样不可再生

| 层 | 文件 | 可重建吗 | 靠什么重建 |
|---|---|---|---|
| L0 原话 | `sessions/*.md`（+ `.gz`） | **不能** | 用户真的说过的话，没有别的地方有 |
| L1 日志 | `log.jsonl` | **不能** | 抽取是模型调用，重算复现不出同一批事实 |
| L1 索引 | `index.sqlite` | 能 | `index.rebuild()` 重放日志 |
| 渲染视图 | `facts.md` / `summaries.md` / `topics.md` | 能 | 由索引渲染；`render_views=False` 时干脆不写 |
| 序号与游标 | `state.json` | 部分 | 丢了只是浪费 id，见下 |

**备份只需要备份前两样。** 这条结论最有用：它把「备份策略」变成「拷两个文件」，
也解释了下面那条追加语义为什么不能松。

## L0：追加语义

`sessions/YYYY-MM-DD.md` 里一行就是一轮：

```
- T-000123 21:04:11 user 我家猫叫团子
- T-000124 21:04:13 assistant 记住了，团子。
```

四个设计点，每一个都是踩过坑才留下的：

- **单行化**：原话里的换行转义成 `\n`（`\r` 单独转义）。记录必须单行完整，
  否则「崩溃只丢尾部残行」这条容错就不成立 —— 一条跨行记录被截断之后，
  前半截看起来是完全合法的一行。`unescape_text` 之后必须一字不差还原，含 CRLF。
- **先占号再写盘**：`T-000123` 全局递增、永不复用，它是事实回引（`turn_ref`）
  的锚点。崩溃最多浪费一个号，绝不会重号。
- **写侧补换行**：追加前先看一眼最后一个字节，不是换行就补一个。不补的话，
  上一条残行会把**下一条整条**吃掉，而读侧丢残行救不了这个 —— 被吃掉的那条
  不在残行里，它就是被残行吃掉了。这里还有一个具体的坑：追加模式必须开
  `a+b` 而不是 `ab`，因为 `ab` 是只写的，`read(1)` 会抛
  `io.UnsupportedOperation`（它同时是 `OSError` 的子类），于是那句「看一眼
  最后一个字节」被**静默**跳过 —— 正好是这个修复要防的症状。
- **`flush` + `fsync`**：这一步压在首字延迟上，但不做就可能在断电时丢掉
  刚说的那句话。

写 L0 的失败姿态是**返回空列表、不抛**：调用方通常就在「他刚说完一句话」的
那条路上，那里的一次磁盘异常不该让整段对话崩掉。

## 归档：一个字节都不删

`turnlog.archive_old_turns` 把**整月**都早于保留期（`retain_months`，默认 24）
的 L0 原话搬进 `sessions.archive/YYYY-MM-DD.md.gz`。

- **按整月判、不在月内切**：只要这个月整体早于截止月，就搬走这个月的每一天。
  在月中间切会让「一个月」这个单位在盘上变成两半，之后再判就得读文件内容。
- **`retain_months = 0` = 永不清理**。负数按写坏了的配置处理，也夹回 0 ——
  读成「保留一个月」会让用户以为关掉了，实际每月都在搬走原话。
- **`read_turns` 透明读回两处**：调用方永远不需要知道这一天的原话住在 `.md`
  还是 `.gz` 里。归档对上层是**不可见**的，这正是「归档」与「删除」的分界。
- **无损 + 幂等**靠三件事：先把内容写进临时文件、再 `os.replace` 到 `.gz`
  （同目录内 = 原子），**最后**才 `unlink` 原 `.md`，崩在任何一步都只会
  「留下没搬完的」，绝不会先删后写；`.gz` 已经在的那一天不重复搬运，只有
  逐字节确认两边同源（= 崩在 replace 与 unlink 之间）才补完最后那一步；
  gzip 记 `mtime=0`，同一份内容两次归档得到同一批字节。
- 返回的是**统计**（搬了几个文件、几个字节、哪些月、跳过几个、错误几条），
  不是 `None` —— 「今天到底搬没搬」要看得到。

原话只有一条路径会真的删除：用户主动重置时的 `purge`（见下）。

## L1：操作日志 + 可重建的索引

`log.jsonl` 一行一条操作，是**唯一事实源**；`index.sqlite` 是它的物化视图。
两者分开的理由只有一句：**索引可以删了重建，日志不能**。

操作种类（`store.ops.apply_op`）：

| op | 做什么 | 为什么要有 |
|---|---|---|
| `ADD` | 写一条新事实 | 主路径 |
| `SUPERSEDE` | 写新的，同时让被取代的那条失效 | 换值不是删除：要能回答「他以前说过什么」 |
| `EDIT` | 改一条的字段 | 用户手改，走 `EDITABLE_FIELDS` 白名单 |
| `INVALIDATE` | 让一条失效（带原因） | 抽取消解之外的外部失效 |
| `PIN` / `CONFIRM` | 钉住 / 确认 | 「恢复」也走 `CONFIRM`，它同时把有效期放回来 |
| `FORGET` | 忘记一条（`archive` / `purge`） | 见「删在每一层各是什么意思」 |
| `MERGE` | 巩固期合并重复项 | 被并的那条标 `merged` 并保留，**不删** |
| `DEROGATE` | 降权（只改 `importance`） | 降权会改排序，不可审计的降权等于悄悄改权重 |
| `SUMMARY` | L2 纪要 | 模型生成、不可再生，所以必须进日志 |
| `TOPIC` | 主动话题 | 同上：只写表的话 `rebuild()` 会把它整丢 |

`apply_op` 必须**幂等**：重放是常态而不是异常。有一处坑写在代码里 —— 读一条
既有事实时**不能**写成 `for k in cur`，`sqlite3.Row` 迭代出来的是**值**不是
列名；这个错误会被 `materialize` 隔离成一行 `bad_ops` 然后继续走，于是
「编辑一条记忆」变成「编辑被丢掉、界面照旧报成功」。

索引是 **schema v1**（`store.index.SCHEMA_VERSION`）。全新项目没有历史数据，
所以迁移链在移植时被**压平成初始建表**：保留一份几百行、谁也跑不到的宿主演进史
是负债。`ensure_schema` 仍然留着版本判据与 `PRAGMA table_info` 自检 ——
判错的代价最多是重跑一次 `CREATE TABLE IF NOT EXISTS`，方向安全。

库开 **WAL**（`journal_mode=WAL` + `synchronous=NORMAL`）。两张表值得单独说：

- `vectors` 上挂着 `text_hash` 与 `model`。少了前者就分不清「这条向量是哪个
  版本的事实编码出来的」：事实改了内容、向量还留着旧的，检索会按旧内容召回。
  少了后者（编码器身份 = 仓库 + 维度）更糟：换一个**同维度**的模型，两个向量
  空间混在一张表里，相似度全是噪声，而统计报一切正常。
- 全文检索走 FTS5 虚表 `facts_fts`，内容指向 `facts`（`content='facts'`）。

`index.rebuild()` 会删掉索引、重放日志。这件事能成立，靠的正是「日志里有全部
内容性操作，索引里只有投影」这条边界；哪一天有谁把一个内容只写进表、忘了写
日志，重建就会静默丢掉它 —— 所以 `SUMMARY` / `TOPIC` 那两段注释写得格外啰嗦。

## state.json：唯一的小可变文件

它不是追加日志，是一个小 JSON，所以可以用「临时文件 + `os.replace`」拿原子性。
两个坑写在 `paths._save_state` 里：

- **临时文件名必须带 pid 与线程 id**。固定叫 `state.tmp` 时，两个写者同时写会让
  `os.replace` 把对方正在写的那个文件搬走 —— 其中一次写入**静默**丢掉，而丢的
  可能正是刚推上去的 `next_seq` / `next_fact_seq`。
- **改状态必须整段在锁里读-改-写**（`mutate_state`）。整理线程手上那份快照中间
  隔着几百毫秒的模型调用，期间前台可能已经推了几轮原话；直接写回会把前台这
  期间的写入盖掉，症状是「她偶尔丢掉刚说过的一轮」。

`state.json` 坏了**不该**让记忆写不下去：读失败就当空的，下一轮从 1 重新编号。
「永不复用」靠的是单调递增，不靠它绝对连续。

## 「删」在每一层各是什么意思

这是最容易含糊过去的一节，所以逐条写死：

| 动作 | 事实行 | 原话（L0） | 日志 | 可恢复吗 |
|---|---|---|---|---|
| `forget(id)`（默认 `archive`） | 标 `forgotten` + 截止时间 | 不动 | 追加一条 `FORGET` | **能** |
| `forget(id, mode="purge")` | **删掉这一行** | 不动 | 追加一条 `FORGET` | 靠日志可以 |
| `confirm(id, accept=True)` | 状态回 `active`，有效期清空 | 不动 | 追加一条 | 它就是恢复 |
| `reset()`（默认 `purge`） | 清空索引 | **删掉** | **删掉** | **不能** |
| `reset(mode="archive")` | 整个目录改名留档 | 同左 | 同左 | 能（改回名字） |

两条容易误读的边界：

- `forget(purge)` 删的只是**事实那一行**。原话与日志都还在 —— 「她不再提这件事」
  与「这件事从没发生过」是两件不同的事，这个库只承诺前者。
- `reset` 返回 `{"mode", "leftover"}`，不是一个 `ok`。因为这条路上「删不掉」是
  常态而不是异常：Windows 上只要还有人开着文件句柄（前台检索、后台整理随时
  可能正在读 `index.sqlite`），`rmtree` 与 `rename` **都会**失败。旧实现把失败
  吞进 `ignore_errors=True`，结果是日志、原话、状态都删了，而事实行**原样留着**
  —— 她照样记得、接口却回成功，而且不可再生的那份已经没了，`rebuild()` 也救
  不回来。所以顺序是：**先把物化层清空**（空表 = 她一条都不记得，这一步与文件
  能不能删掉无关）→ 再删不可再生的文件 → **如实报出没删掉的**（`leftover`）。
  这里还有一个死锁陷阱：`index.wipe` 自己也要拿 `uid` 那把锁，而
  `threading.Lock` 不可重入 —— 把它套进 `with _lock(uid)` 会当场死锁，所以它
  必须在锁外单独调用。
